## 1. 这个项目是什么

一个**纯本地**的 HarmonyOS 应用：用户自定义「当…则…」联动规则，用模拟环境数据（温度/光照/湿度/时段/在室）驱动规则引擎，观察 5 台设备如何联动、执行顺序如何、多条规则争用同一设备时如何裁决，并把规则、设备状态、最近 50 条执行记录持久化到本地。

**没有**真实硬件、网络、云端、账号体系。所有业务判断都在一个不依赖 HarmonyOS API 的纯逻辑模块里完成。

| 项 | 值 |
| --- | --- |
| 语言 / 框架 | ArkTS + ArkUI（Stage 模型，声明式 UI） |
| SDK | HarmonyOS 5.0.5 / API 17（`compatibleSdkVersion: 5.0.5(17)`） |
| 持久化 | `@kit.ArkData` → `preferences` |
| 测试 | `node:test`（20 条，纯逻辑）+ `@ohos/hypium`（14 条，DevEco 内运行） |
| 源码规模 | 约 2460 行（不含资源与测试数据） |

### 4.1 三层 + 一个测试层

│ 表现层  pages/Index.ets（1345 行，唯一页面）              │

┌───────────────▼─────────────────────────────────────────┐
│ 业务层  engine/RuleEngine.ts（664 行）+ DefaultData.ts    │
│   纯函数：判定、排序、冲突裁决、记录、序列化、自检          │

┌───────────────▼─────────────────────────────────────────┐
│ 数据层  viewmodel/DormStore.ets + repository/StorageService.ets │
│   Preferences('dormlink_state') 单 JSON 快照，一次 flush   │
└─────────────────────────────────────────────────────────┘

**为什么引擎必须"纯净"**：只有不依赖 ArkUI，才能用 `node --test` 在没有模拟器的情况下跑真实断言；如果判定逻辑写在组件里，测试就得启动整个页面。这是本项目最重要的一条架构约束，改动时不要破坏（不要往 `RuleEngine.ts` 里加 `import { ... } from '@kit.xxx'`）。

### 4.2 一次「执行联动演练」的完整链路

```
用户点「执行联动演练」
  → Index.runOnce()                       [Index.ets ~192]
      evaluate(this.env, this.devices, this.rules)   [RuleEngine.ts ~315]
          normalizeEnvironment()   越界裁剪、NaN 回退
          validateRule()           剔除非法规则，写 warnings
          isRuleTriggered()        conditions 之间 AND
              matchCondition()     单条件比较，NaN/未知量 → false
          compareRules()           按 (priority 升序, id 升序) 排序
          逐个 action：
              occupied.has(deviceId) ? 拦截 + ConflictRecord
                                     : 占用通道 + 写设备 + before→after 记录
      ← ExecutionResult { devices, records, conflicts, triggeredRuleIds,
                          executedCount, blockedCount, warnings }
  → 整体赋值给 @State（devices / records / conflicts / triggered / ...）
  → ArkUI 刷新四个页签
  → DormStore.persist()  [DormStore.ets ~99]
        serializeState() → JSON 字符串
        StorageService.save() → put + flush
```

### 4.3 冷启动恢复链路

```
EntryAbility → 加载 pages/Index
  → Index.aboutToAppear()                 [Index.ets ~87]
      DormStore.restore(ctx)              [DormStore.ets ~47]
          StorageService.init()   失败 → 默认方案 + "存储服务不可用"
          StorageService.load()   → deserializeState()
                                   null → 默认方案 + "未检测到有效存档"
          validateRule 逐条校验，设备/规则为空 → 默认方案 + "存档损坏"
          成功 → records/conflicts 各截断到 50 条

```

## 6. 核心数据模型

全部定义在 `RuleEngine.ts` 第 14–115 行，**只改这里**，不要在其他文件重复定义。

| interface | 关键字段 | 说明 |
| --- | --- | --- |
| `Environment` | `temperature` `illuminance` `humidity` `hour` `occupancy` | 5 项模拟输入；区间见 §7.3 |
| `DeviceState` | `id` `name` `power` `value` `unit` | `value` 语义随设备变：亮度% / 目标温度℃ / 开合度% / 风速档 / 加湿档 |
| `Condition` | `metric` `op` `value` | `occupancy` 用 1/0 表示真/假 |
| `DeviceAction` | `deviceId` `power` `value` | 一条规则可含多个动作，作用于不同设备 |
| `AutomationRule` | `id` `name` `enabled` `priority` `conditions[]` `actions[]` | **priority 数值越小优先级越高**；conditions 之间是 AND |
| `DeviceChange` | `beforePower/afterPower` `beforeValue/afterValue` | 执行日志的核心证据 |
| `ExecutionRecord` | `order` `ruleId` `conditions` `change` `blocked` `note` | `blocked=true` 表示该动作被更高优先级规则拦截 |
| `ConflictRecord` | `deviceId` `winnerRuleId` `loserRuleId` `reason` | 一次争用一条 |
| `ExecutionResult` | `devices` `records` `conflicts` `triggeredRuleIds` `executedCount` `blockedCount` `warnings` | 一次演练的完整输出 |
| `PersistedState` | `version` `environment` `devices` `rules` `records` `conflicts` `savedAt` | 落盘结构；`version` 目前固定为 1 |

两个类型别名值得记住：`MetricKey`（5 个环境量）、`DeviceId`（5 台设备）。UI 里的下拉框选项数组 `METRIC_KEYS` / `OP_KEYS` / `DEVICE_KEYS` 必须与这两个联合类型保持一致，**加设备/加环境量时三处一起改**（见 §11）。

## 7. 规则引擎：关键函数与业务规则

### 7.1 函数速查（按调用顺序）

| 函数 | 行号 | 行为 | 边界 / 异常 |
| --- | --- | --- | --- |
| `clampMetric(metric, raw)` | 173 | 把数值裁剪到该环境量的合法区间 | `hour` 用 `Math.floor` 向下取整；`!Number.isFinite` 一律返回**下界** |
| `normalizeEnvironment(raw)` | 192 | 逐项裁剪，`occupancy` 只认 `=== true` | `raw` 为 null → 返回默认环境 |
| `readMetric(env, metric)` | 211 | 取数值；`occupancy` 转 1/0 | 未知 metric → `NaN` |
| `matchCondition(env, cond)` | 223 | 单条件比较，支持 LT/LE/GT/GE/EQ/NE | 未知量、非法 op、NaN 参与比较 → `false` |
| `isRuleTriggered(env, rule)` | 240 | 所有 conditions 都满足才 true | `enabled=false`、空 conditions → false |
| `validateRule(rule)` | 252 | 返回问题描述数组，空数组 = 合法 | 空条件、空动作、未知设备、非数值优先级都会被拦 |
| `compareRules(a, b)` | 274 | priority 升序；相同则 id 字典序 | 保证排序稳定、结果可复现 |
| `evaluate(rawEnv, devices, rules)` | 315 | 主入口，返回 `ExecutionResult` | 空规则/空设备/null 规则 → 安全返回 + warnings |
| `serializeState` / `deserializeState` | 437 / 447 | JSON 往返 | 损坏 JSON / 缺字段 → `null` |
| `runSelfTest()` | 520 | 应用内自检，跑 12 条断言（正常 5 / 边界 3 / 异常 4） | 供日志页「生成测试报告」使用 |

### 7.2 冲突裁决：整个项目最需要看懂的一段

`evaluate()` 里用一张 `Map<DeviceId, string>` 记录**每个设备通道被哪条规则占用**：

```
命中规则按 (priority, id) 排序
  ↓
遍历每条规则的每个动作：
    通道已被占用 → 不写设备，生成 ConflictRecord + blocked=true 的记录，continue（继续处理该规则的下一个动作）
    通道空闲     → 占用通道，写设备状态，记录 before→after
```

三个容易误解的点：

1. **优先级数字小的赢**。R002 的 priority=20，R005 的 priority=50，所以 S2 场景里空调是 R002 说了算 → 最终「开」。
2. **拦截是逐设备的，不是逐规则的**。R005 的空调动作被拦，但它对主灯、风扇的动作照常执行。代码里用的是 `continue` 而不是 `break`。
3. **每次演练都从传入的 `devices` 重新开始**，不会累加上次结果。同一输入执行两次，终态必然一致（这条有测试守着）。

### 7.3 6 条默认规则（`DefaultData.ts`）

| ID | 名称 | 优先级 | 条件 | 动作 | 备注 |
| --- | --- | --- | --- | --- | --- |
| R001 | 夜间归寝照明 | 10 | hour ≥ 22 **且** occupancy = 1 | 主灯 开 60% | 双条件 |
| R002 | 高温自动制冷 | 20 | temperature ≥ 28 | 空调 开 26℃ | 与 R005 争空调 |
| R003 | 强光自动遮阳 | 30 | illuminance ≥ 800 | 窗帘 关 0% | — |
| R004 | 干燥加湿 | 25 | humidity ≤ 35 **且** occupancy = 1 | 加湿器 开 2 档 | 双条件 |
| R005 | 无人节能 | 50 | occupancy = 0 | 主灯/空调/风扇 全关 | 优先级最低，动作最多 |
| R006 | 晨间唤醒 | 15 | hour ≥ 7 **且** hour < 9 | 窗帘 开 100%、主灯 开 40% | **默认停用** |

环境量合法区间：温度 `[-10, 50]`、光照 `[0, 2000]`、湿度 `[0, 100]`、时段 `[0, 23]`（向下取整）、在室 `{0,1}`。

### 7.4 4 组预设场景

| ID | 名称 | 环境 | 用来验证什么 |
| --- | --- | --- | --- |
| S1 | 夏夜归寝 | 30℃ / 60lux / 58% / 23点 / 有人 | R001 与 R002 同时命中，执行顺序 R001 → R002 |
| S2 | 午后无人·冲突 | 31℃ / 900lux / 42% / 14点 / 无人 | **核心演示**：R002 与 R005 争空调，R002 胜出，R005 空调动作被拦 |
| S3 | 干燥清晨 | 18℃ / 280lux / 28% / 8点 / 有人 | R004 触发；启用 R006 后窗帘通道产生新冲突 |
| S4 | 深夜无人 | 22℃ / 5lux / 50% / 2点 / 无人 | 只有 R005 生效，全部耗能设备关闭 |

## 8. 持久化

| 项 | 说明 |
| --- | --- |
| 存储 | `preferences.getPreferences(ctx, 'dormlink_state')` |
| 键 | `snapshot`（完整 JSON）、`saved_at`（毫秒时间戳） |
| 写入时机 | 每次业务变更后 `DormStore.persist()` → `put` + `flush` |
| 记录上限 | `records` / `conflicts` 各保留最近 50 条（`slice(0, 50)`） |
| 版本字段 | `PersistedState.version` 目前固定 1；**加字段时应递增并写迁移分支** |

恢复的三种降级（都返回默认方案，只是提示文案不同）：

| 情况 | 提示 |
| --- | --- |
| 存储服务初始化失败 | 「存储服务不可用，已加载默认方案（未恢复）」 |
| 无存档 / JSON 损坏 | 「未检测到有效存档，已加载默认方案」 |
| 存档里设备或规则为空 | 「存档内容损坏或不完整，已安全回退默认方案」 |

> 注意：恢复阶段有 `@State restoring: boolean` 保护。原因是 Slider 初始化会触发一次 `onChange`，若不加保护会把「已从 Preferences 恢复…」的提示覆盖成「已保存」。改页面时不要删这个标志。

## 11. 常见改动指南（Recipe）

### 11.1 新增一个环境量（例如「CO₂ 浓度」）

必须**六处同步改**，漏一处就编译不过或运行异常：

1. `RuleEngine.ts`：`MetricKey` 联合类型加 `'co2'`
2. `RuleEngine.ts`：`Environment` interface 加 `co2: number`

## 13. 已知的坑（都真实踩过，别再踩）

| 坑 | 现象 | 正确做法 |
| --- | --- | --- |
| **`@Builder` 值传递不刷新** | 把 `this.devices[i].value` 当参数传给 `@Builder`，状态变了界面不动（本项目踩过 3 次：滑块、设备卡、统计数字） | `@Builder` 内部直接读 `this.xxx`，参数只传不变的标识（如 `key`、`id`）；或把状态拼进 `ForEach` 的 key |
| **`@State tabIndex` 编译报错** | `This comparison appears to be unintentional because the types '(index:number)=>CommonAttribute' and 'number' have no overlap` | `tabIndex`、`tabColor`、`tabBar` 都是 ArkUI 内置属性名，状态变量改叫 `currentTab`、方法改叫 `resolveNavColor` |
| **`padding` 对象写法让整页塌陷** | 给 Scroll 内的 Column 用 `.padding({ left, right, top, bottom })`，该页内容变空白（联动台正常、演练页全白） | 用 `.padding(SpaceToken.lg).margin({ bottom: 80 })` 代替对象写法 |
| **`node --test tests/node/` 失败** | `Cannot find module ...\tests\node` | `tests/node/package.json` 让 Node 把目录当模块入口。用 `cd tests/node && npm test` 或 `node --test tests/node/*.test.mjs` |
| **Toast 被覆盖层挡住** | 规则编辑器里保存失败，看不到「规则不合法」提示 | toast 渲染在 `Stack` 最外层、所有覆盖层之后 |
| **`Select` 只显示箭头** | 下拉框没文字 | `Select` 必须同时设 `.selected()` 和 `.value()` |
| **恢复提示被覆盖** | 重启后提示一闪变成「已保存」 | 保留 `@State restoring` 保护，初始化期间不触发持久化 |
| **ohosTest 命令行跑不起来** | `aa test` 返回 0 但无输出 | 该镜像的 testRunner 未随 HAP 打包，只能在 DevEco 内右键运行；对外证据统一用 Node 侧用例 |
| **执行记录被覆盖** | 每次演练后日志页只剩最后一批记录，`slice(0, 50)` 的截断逻辑形同虚设 | `runOnce()` 里不能 `this.records = result.records`，要追加并保留最近 50 条（见 `appendRecords()`）；摘要（触发/执行/拦截）另存 `lastTriggered` 等字段，因为「本次」与「历史」语义不同 |
| **覆盖层 Scroll 内容居中** | 规则/设备详情页内容不足一屏时，顶部出现一大块空白 | 覆盖层里的 `Scroll` 必须加 `.align(Alignment.Top)` |
| **测试跑在 Node 18 上** | `ERR_UNKNOWN_FILE_EXTENSION: Unknown file extension ".ts"`，或只报 2 个 test 全失败 | 纯逻辑测试依赖 Node ≥ 22.6 的 type-stripping；若把 DevEco 自带 Node（v18）加进了 PATH，`npm test` 会用它跑。`tests/node/package.json` 已声明 `engines.node >= 22.6` |

## 14. 排查手册

| 现象 | 先查什么 |
| --- | --- |
| 编译报 `Schema validate failed` | `module.json5` 里加了不支持的字段（如 `testRunner`）；对照官方 schema 删掉 |
| 编译报 ArkTS 类型错误 | 是否用了 `any`、对象展开 `...`、可选链 `?.`——ArkTS 不支持，改成显式字段构造 |
| 界面空白但无报错 | 大概率是布局塌陷（见 §13 的 padding 坑），或 `@Builder` 里读不到状态 |
| 重启后数据没恢复 | 日志页看提示文案：三种降级分别对应存储不可用 / 无存档 / 存档损坏；也可 `hdc shell cat /data/app/el2/100/base/com.xuhao.dormlink/haps/entry/preferences/dormlink_state` 直接看存档 |
| 演练结果与预期不符 | 先打印 `triggeredRuleIds` 确认排序，再检查是否被更高优先级规则占了通道 |
| 测试全绿但界面不对 | 测试只覆盖引擎，UI 问题要看 `@State` 是否被整体赋值（`this.devices = result.devices`，不要 `push` 进原数组） |

## 15. 术语表
