## 1. 引言

### 1.1 编写目的

在编码之前明确用户需求、业务范围、数据模型、模块接口、分工、测试与验收方式，作为设计、实现、测试与期末报告的共同依据。本文档与仓库源码、测试日志、个人报告保持一致，需求条目均可通过运行应用逐条验收。

### 1.2 项目背景与范围

宿舍里的灯、空调、窗帘、风扇、加湿器通常由人分别操作，缺少统一的"满足条件时自动执行"的联动机制；而真实硬件与云平台不在本课程范围内。本项目构建一个**纯本地、可模拟、可持久化**的自动化规则编排环境：用户自定义规则，用 Mock 环境数据驱动规则引擎计算设备动作，观察执行日志与冲突，并在调整规则后验证效果。

**范围内**：规则 CRUD 与启停、Mock 环境调整、规则引擎计算、冲突优先级裁决、执行日志、Preferences 持久化与进程重启恢复、单元测试。
**范围外**：真实硬件控制、云同步/账号体系、AI 生成规则、多用户协作、3D 建模。

## 2. 需求与问题分析

### 2.1 用户与核心场景

用户是希望统一管理宿舍设备的学生。典型使用情境：夏季午后宿舍无人但室温很高，"高温自动制冷"想开空调，"无人节能"想关空调，两者冲突；用户需要看到谁被采纳、谁被拦截，并据此调整规则。

### 2.2 功能需求（可验收）

| 编号 | 需求 | 验收方式 |
| --- | --- | --- |
| FR-01 | 提供 ≥4 类可控设备；实际实现 5 类：主灯、空调、窗帘、风扇、加湿器 | 联动台/设备卡片可见 5 张卡，状态随演练变化 |
| FR-02 | 提供 ≥3 项可调 Mock 环境数据；实际实现 5 项：温度、光照、湿度、时段、在室状态 | 联动台 4 个滑块 + 1 个开关可调并即时显示数值 |
| FR-03 | 支持新增、修改、启停规则，规则数 ≥4；默认内置 6 条 | 规则页新增/编辑/删除/Toggle，保存后立即重新演练 |
| FR-04 | 至少 1 条由两个条件共同决定的规则；实际 R001、R004、R006 为双条件 | 规则卡显示"条件1 且 条件2"；单元测试验证 AND 语义 |
| FR-05 | 规则引擎根据真实输入计算触发结果，记录触发条件、设备变化、执行顺序 | 日志页每条记录含序号、优先级、条件快照、before→after |
| FR-06 | 冲突控制有明确执行顺序/优先级；同设备仅最高优先级规则写入，其余被拦截并记录 | 载入 S2 场景出现冲突提示与 ConflictRecord；一键修复后冲突消失 |
| FR-07 | ≥2 组环境场景模拟演练；实际提供 4 组 | 演练页 4 张场景卡，点击即载入环境并执行 |
| FR-08 | 保存设备设置、规则和执行记录；结束进程重开仍能恢复 | 修改规则 → 杀进程 → 重启 → 日志页显示"已从 Preferences 恢复…"且数据一致 |
| FR-09 | 异常输入不崩溃，给出可读告警 | 越界/NaN/非法规则/损坏存档均有 warnings 与单元测试覆盖 |

### 2.3 非功能需求

- **可运行**：DevEco Studio 可导入、编译、部署到模拟器/真机，无静态页面堆砌。
- **可复现**：同一输入两次演练得到相同设备终态、触发顺序与执行记录（测试 `[边界 5]` 验证）。
- **可维护**：规则引擎为不依赖 HarmonyOS API 的纯逻辑模块，UI 与业务解耦。
- **性能**：单次演练 6 条规则 / 5 个设备，计算量常量级，无需异步线程。

## 3. 数据与状态分析

### 3.1 主要数据模型

| 对象 | 关键字段与类型 | 业务含义 | 存储/读取 |
| --- | --- | --- | --- |
| `Environment` | temperature:number, illuminance:number, humidity:number, hour:number, occupancy:boolean | 可调整的模拟环境输入 | 内存 @State + Preferences 快照 |
| `DeviceState` | id:DeviceId, name:string, power:boolean, value:number, unit:string | 5 类设备的当前状态；power=开关，value=亮度%/目标温度℃/开合度%/风速档/加湿档 | 内存 @State + Preferences 快照 |
| `Condition` | metric:MetricKey, op:CompareOp, value:number | 单条触发条件；occupancy 用 1/0 表示真假 | 随规则持久化 |
| `DeviceAction` | deviceId:DeviceId, power:boolean, value:number | 单条设备动作 | 随规则持久化 |
| `AutomationRule` | id:string, name:string, enabled:boolean, priority:number, conditions:Condition[], actions:DeviceAction[], description:string | 联动规则；conditions 之间 AND，priority 数值越小越优先 | Preferences 快照 |
| `ExecutionRecord` | order:number, ruleId, ruleName, priority, conditions:Condition[], change:DeviceChange, blocked:boolean, note:string | 一次动作的执行证据：序号、触发条件快照、设备 before→after、是否被拦截 | Preferences 保留最近 50 条 |
| `ConflictRecord` | deviceId, winnerRuleId, loserRuleId, reason:string | 冲突裁决证据 | Preferences 保留最近 50 条 |
| `PersistedState` | version, environment, devices, rules, records, conflicts, savedAt | Preferences 中单个 JSON 快照的完整结构 | `preferences.getPreferences(ctx,'dormlink_state')` |

### 3.2 状态变化与模块间数据流

```
用户在联动台拖动滑块 / 切换在室
  → Index.setEnvValue / setOccupancy 更新 @State env
  → 点击「执行联动演练」或载入场景
  → Index.runOnce() 调用 RuleEngine.evaluate(env, devices, rules)
      ├─ normalizeEnvironment：越界裁剪、NaN 降级，收集 warnings
      ├─ validateRule：剔除非法规则，收集 warnings
      ├─ isRuleTriggered：逐条 AND 判定，得到命中规则
      ├─ compareRules：按 (priority 升序, id 升序) 稳定排序
      └─ 顺序执行动作 + Map<DeviceId, ruleId> 冲突裁决
  → 返回 ExecutionResult（设备终态、records、conflicts、warnings）
  → 整体赋值回 @State（devices / records / conflicts / warnings / triggered）
  → ArkUI 触发四个页签 UI 刷新
  → DormStore.persist() → serializeState → StorageService.save() → Preferences.flush()
```

冷启动反向数据流：`Index.aboutToAppear → DormStore.restore → StorageService.load → deserializeState → applySnapshot → @State 回填`。

### 3.3 关键业务规则

1. 停用规则、无条件规则、校验失败规则均不参与演练。
2. 条件之间为 AND；`occupancy` 用数值 1/0 参与统一比较。
3. 命中规则按优先级升序执行；优先级相同按 id 升序，保证顺序可复现。
4. **冲突裁决**：以 `deviceId` 为控制通道，同一演练周期内先执行的高优先级规则占用该通道；后续规则对同一设备的动作被拦截，写入 `ConflictRecord`，但同一规则对其他设备的动作照常执行。
5. 每次演练以传入的设备状态为起点（不是累加到上次结果），保证可复现。

## 4. 边界与异常分析

| 类型 | 具体情况 | 处理方式 | 验证用例 |
| --- | --- | --- | --- |
| 边界 1 | 阈值临界值（28℃、35%、hour=0/23） | 比较运算含等号（GE/LE），hour 向下取整并裁剪到 [0,23] | `[边界 1]` `[边界 2]` |
| 边界 2 | 空规则列表 / 全部停用 / 空设备列表 | 设备状态原样返回，产生 warnings 提示，不抛异常 | `[边界 3]` `[边界 4]` |
| 边界 3 | 同一设备被多规则争用 | 优先级裁决 + 拦截日志，不静默覆盖 | `[正常 4]` `[正常 5]` |
| 异常 1 | 环境数值越界、NaN、null 环境对象 | `clampMetric` 裁剪到合法区间；null 回退默认环境；写 warnings | `[异常 1]` `[异常 6]` |
| 异常 2 | 未知环境量 / 非法运算符 / NaN 阈值 | `matchCondition` 返回 false，不抛异常 | `[异常 2]` |
| 异常 3 | 空条件、空动作、未知设备、NaN 优先级、null 规则表 | `validateRule` 拦截并写 warnings；非法规则不参与演练 | `[异常 3]` `[异常 7]` |
| 异常 4 | Preferences 初始化失败 / 存档 JSON 损坏 / 字段缺失 | 降级为默认方案并在界面显示原因；`deserializeState` 返回 null | `[异常 5]`、日志页提示条 |

## 5. 系统架构与模块划分

### 5.1 分层架构

```
┌──────────────────────────────────────────────┐
│ 表现层  entry/src/main/ets/pages/Index.ets    │
│  联动台 / 规则 / 演练 / 日志 四个 Tab + 规则编辑器 │
│  @State 驱动，@Builder 复用，Slider/Toggle/Select │
└───────────────┬──────────────────────────────┘
                │ 调用纯函数 / 读写 AppSnapshot
┌───────────────▼──────────────────────────────┐
│ 业务层  engine/RuleEngine.ts + DefaultData.ts  │
│  条件判定 / 排序 / 冲突裁决 / 日志 / 序列化       │
│  （不依赖 HarmonyOS API，可被 Node 直接测试）      │
└───────────────┬──────────────────────────────┘
                │ AppSnapshot / PersistedState
┌───────────────▼──────────────────────────────┐
│ 数据层  viewmodel/DormStore.ets                │
│        repository/StorageService.ets           │
│  Preferences('dormlink_state') 单 JSON 快照     │
└──────────────────────────────────────────────┘
```

### 5.2 模块职责与接口关系

| 模块 | 主要职责 | 输入 → 输出 | 负责人 |
| --- | --- | --- | --- |
| `pages/Index.ets` | 四个页签 UI、用户交互、@State 状态管理、调用业务与数据层 | 用户操作 / AppSnapshot → 界面状态与持久化请求 | 当前：徐豪；后续 UI / 设备控制增强：钱志刚 |
| `engine/RuleEngine.ts` | 条件判定、规则排序、冲突裁决、执行记录、异常降级、序列化 | (env, devices, rules) → ExecutionResult | 徐豪 |
| `engine/DefaultData.ts` | 默认设备、6 条规则、4 组场景、环境量合法区间 | 常量 → DEFAULT_* / SCENE_PRESETS | 徐豪 |
| `viewmodel/DormStore.ets` | 内存态与持久化快照转换、恢复降级 | Context / AppSnapshot → RestoreResult / boolean | 徐豪 |
| `repository/StorageService.ets` | Preferences 读写、flush、异常捕获 | (string, number) → boolean / string | 徐豪 |
| `ohosTest` + `tests/node` | 单元测试与真实运行日志 | Mock 输入 → 断言结果 | 当前：徐豪；后续独立复核与新增用例：钱志刚 |

### 5.3 关键模块接口定义

| 接口 / 方法 | 输入参数 | 返回值 | 异常 / 边界处理 |
| --- | --- | --- | --- |
| `evaluate(rawEnv, devices, rules)` | Environment, DeviceState[], AutomationRule[] | ExecutionResult | null 环境回退默认值；null/空规则返回原设备 + warnings；越界数值裁剪 |
| `isRuleTriggered(env, rule)` | Environment, AutomationRule | boolean | 停用/空条件/非法条件返回 false |
| `matchCondition(env, cond)` | Environment, Condition | boolean | 未知量、非法 op、NaN 一律 false |
| `validateRule(rule)` | AutomationRule | string[] | 返回问题描述数组，空数组表示合法 |
| `compareRules(a, b)` | 两条规则 | number | 优先级相同按 id 字典序，保证稳定 |
| `serializeState(state)` / `deserializeState(text)` | PersistedState / string | string / PersistedState\|null | null 返回空串；损坏 JSON 或缺字段返回 null |
| `DormStore.restore(ctx)` | common.Context | RestoreResult | 存储失败/无存档/损坏 → 默认方案 + 原因文本 |
| `DormStore.persist(ctx, snap, savedAt)` | Context, AppSnapshot, number | boolean | 序列化失败或写入异常返回 false |
| `StorageService.save(text, savedAt)` | string, number | boolean | 未初始化或异常返回 false，不向上抛 |

## 7. 测试设计

### 7.1 策略

规则引擎为纯逻辑模块，全部输入用本地 Mock 对象构造，无需真实设备。两套测试共用同一份产品源码：

- `tests/node/rule-engine.test.mjs`：`node:test` + `assert`，Node 22 type-stripping 直接 import `.ts` 源码，**20 条，20 通过**（真实命令输出见 `docs/测试运行日志.md`）。
- `entry/src/ohosTest/ets/test/RuleEngine.test.ets`：`@ohos/hypium`，14 条，在 DevEco Studio / 设备上运行。

### 7.2 三类用例

| 类别 | Mock 输入 | 预期结果 |
| --- | --- | --- |
| 正常 | 温度 30℃ + 仅 R002 | 空调开启 26℃，生成 1 条 order=1 的执行记录，before→after 正确 |
| 正常 | S1 夏夜归寝（23 点、有人、30℃） | R001(p10) → R002(p20) 顺序执行 |
| 正常 | S2 午后无人（31℃、900lux、无人） | R002 胜出保留空调开启，R005 空调动作被拦截，主灯/风扇仍关闭 |
| 边界 | 温度 28 / 27，湿度 35 / 36，hour 0 / 23 | 含等号阈值在临界值命中，其余不命中 |
| 边界 | 空规则表、空设备表、全部规则停用 | 设备不变、无执行记录、给出告警 |
| 异常 | 温度 999、湿度 NaN、null 环境 | 裁剪/回退 + warnings，引擎不崩溃 |
| 异常 | 空条件、未知设备、NaN 优先级、损坏 JSON | 非法规则被拦截；`deserializeState` 返回 null |
