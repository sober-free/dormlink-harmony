### 执行过程中修复的三个真实缺陷

1. **@State 更新后界面不刷新**：`@Builder` 的值传递参数（`MetricSlider` 的 `value`、`DeviceCard(d)`）在状态变化后不会重建，`ForEach` 以 `d.id` 作 key 也会复用旧节点，导致重启后存档已恢复、界面却仍显示默认值。修复：改为在 `@Builder` 内直接读 `this.envValue(key)`，并把 `ForEach` 的 key 拼上 `power` / `value` / `priority` 等状态字段。
2. **规则编辑器下拉框空白**：`Select` 只设了 `.selected(index)` 未设 `.value(text)`，界面只显示箭头。修复：补 `.value(metricLabel / opLabel / deviceName)`。
3. **恢复提示被初始化回调覆盖**：Slider 与 Toggle 在回填时会触发 `onChange`，进而调用保存逻辑，把「已从 Preferences 恢复…」覆盖成「本次改动已写入…」。修复：回调中先比较新值与原值，相同则直接返回。

## 1. 导入与编译

1. DevEco Studio → `File > Open` → 选择 `dormlink-harmony` 根目录。
2. 等待 `Sync` 完成；若提示 `ohpm install`，允许执行。
3. 若提示签名错误：`File > Project Structure > Project > Signing Configs`，勾选 `Automatically generate signature` 后重新 Sync。
4. 若 SDK 版本不匹配：把根 `build-profile.json5` 里的 `compatibleSdkVersion` / `targetSdkVersion` 改为本机已安装的 API 版本（如 `4.1.0(11)`）。
5. 选择 HarmonyOS 模拟器或真机，点击 `Run 'entry'`。
6. 首次启动应看到 6 条默认规则、5 个设备（全部 OFF）、顶部提示"未检测到有效存档，已加载默认方案"。

## 2. 运行 ohosTest 单元测试

1. 在 Project 视图展开 `entry/src/ohosTest/ets/test`。
2. 右键 `List.test.ets` 或 `ohosTest` 目录 → `Run 'Tests in entry'`。
3. 选择模拟器/真机，等待 14 条用例执行完毕，截图保存 **Run 面板的通过结果**（`14 tests passed`）。
4. 也可在终端运行纯逻辑测试作为交叉验证：
   ```bash
   node --test tests/node/rule-engine.test.mjs
   ```
   需要 Node.js ≥ 22.6，输出应与 `docs/测试运行日志.md` 一致（20/20 通过）。

录制要点：
- 窗口最小化时 `PrintWindow` 只能抓到纯黑，脚本里先 `IsIconic` 判断并 `ShowWindow(SW_RESTORE)`。
- 桌面图标文字在 y=805，可点区域在图标本体，需上移约 70px 再点击。
- hdc 服务偶发卡死（所有 `hdc shell` 无回显），`hdc kill` + `hdc start` 可恢复。

录屏要点：
- 全程录进顶部状态条（存档时间 / "已恢复存档"标记），这是持久化证据的关键。
- 结束进程请用系统「最近任务 → 上滑关闭」或 DevEco 的 `Stop`，不要只按 Home 键（后台保留不等于进程重启）。
- 重启后先停 2 秒再操作，让"已从 Preferences 恢复…"提示清晰可读。

## 5. 常见问题

| 现象 | 处理 |
| --- | --- |
| 编译报 SDK 版本错误 | 修改根 `build-profile.json5` 的 SDK 版本后 Sync |
| 编译报签名缺失 | 开启自动签名 |
| `node --test` 报 `Unknown file extension ".ts"` | Node 版本过低，升级到 ≥ 22.6 |
| 重启后没有恢复提示 | 确认是"强制结束进程"而非切后台；检查日志页告警是否有"存档写入失败" |
| 规则编辑保存时提示"规则不合法" | 检查是否删除了全部条件/动作，或阈值输入框为空 |

## 6. 2026-11-09 重录记录（UI 改版后，方法已更新）

UI 重做（米家式配色 + 分组卡片 + 行式列表 + 规则/设备详情页）后，旧截图与视频全部重录。

### 6.1 与旧方法的差异

| 环节 | 旧做法（2026-11-09 上午） | 现做法 |
| --- | --- | --- |
| 截图 | `snapshot_display` 单张 | 同左，但改为**按控件树文本定位**再点击（不硬编码坐标） |
| 录屏 | Win32 `PrintWindow` 抓模拟器窗口 18 fps | **设备端 `snapshot_display` 循环**，约 16 fps，540×1166 |
| 合成 | imageio + ffmpeg | ffmpeg（`-framerate` 取「帧数 ÷ 实际耗时」） |

**为什么放弃 PrintWindow**：该模拟器窗口尺寸被强制为 438×779，与屏幕比例（1260×2720）不符，窗口把屏幕**底部约 166px 裁掉**，tab bar 直接看不到；`SetWindowPos` 改尺寸会被模拟器改回去。

### 6.2 现用命令

```bash
# 1) 设备端后台连续截帧（约 16 fps，540×1166，单帧 ~40KB）
hdc shell "rm -rf /data/local/tmp/frames /data/local/tmp/stop; mkdir -p /data/local/tmp/frames"
hdc shell "nohup sh -c 'i=0; while [ ! -f /data/local/tmp/stop ]; do i=\$((i+1)); \
  snapshot_display -f /data/local/tmp/frames/\$i.jpeg -w 540 -h 1166 >/dev/null 2>&1; done' >/dev/null 2>&1 &"

# 2) 另一条连接上正常用 uitest 驱动界面（截帧在设备端跑，不占 hdc 通道）

# 3) 结束并打包回传
hdc shell "touch /data/local/tmp/stop"
hdc shell "cd /data/local/tmp && tar czf f.tgz frames"
hdc file recv /data/local/tmp/f.tgz ./f.tgz && tar xzf f.tgz

# 4) 合成（帧率 = 帧数 ÷ 分镜实际耗时，否则视频会被拉长）
ffmpeg -y -framerate 15.86 -start_number 1 -i frames/%d.jpeg \
  -c:v libx264 -preset medium -crf 25 -pix_fmt yuv420p -movflags +faststart demo-recording.mp4
```

### 6.3 新增踩坑

| 坑 | 现象 | 正确做法 |
| --- | --- | --- |
| **hdc 传绝对 Windows 路径** | `file recv` 报 `open path:C:/.../C:/...`，文件拿不回来 | 切到目标目录后用**相对文件名**：`subprocess.run([...], cwd=dir)` |
| **`载入` 文本歧义** | 点「载入」没反应 | 说明文字里也含「载入」，必须 `exact=True` 精确匹配 |
| **`关闭` 文本歧义** | 点关闭关不掉自检报告 | 用例描述里有「…仍执行关闭」，同样要精确匹配；报告页的关闭按钮在最底部 |
| **长页面元素不在视口** | `执行联动演练` / `主灯` 找不到 | 用「滚动直到出现再点」的封装（`tap_scroll`），别假设一屏能放下 |
| **Slider 拖动** | 按数值比例算起点会跑偏 | 从轨道中点按下再拖到目标位置（值跟随手指），不要用「当前值 ÷ 最大值」 |
| **截帧帧率不等于设定值** | 按 11 fps 编码得到 227 秒，实际只录了 158 秒 | 编码帧率必须用「总帧数 ÷ 分镜实际耗时」反算 |
